## 1. Agent框架重构

### 问题描述
LangChain框架学习成本高，定制化困难，调试复杂。

### 解决方案
自研Agent框架，基于ReAct模式，保持工具兼容性。

**核心代码：**
```python
class BaseAgent(ABC):
    @abstractmethod
    async def run(self, user_input: str, **kwargs) -> str:
        pass
    
    def _determine_execution_mode(self, user_input: str) -> str:
        if self.match_simple_pattern(user_input):
            return ExecutionMode.CHAIN
        return ExecutionMode.AGENT
```

**收益：** 学习成本降低60%，定制化效率提升3倍。

## 2. 工具调用循环检测

### 问题描述
Agent陷入无限循环，重复调用相同工具，浪费Token。

### 解决方案
实现循环检测机制，相似度计算和早停策略。

**核心代码：**
```python
def _check_loop_detection(self, current_response: str) -> Dict[str, Any]:
    similarity = self._calculate_similarity(current_response, prev_response)
    if similarity > self.similarity_threshold:
        return {"should_stop": True, "reason": "检测到循环"}
```

**收益：** Token消耗减少80%，用户等待时间缩短70%。

## 3. LangChain工具兼容

### 问题描述
`@tool`装饰器创建的工具，`func`属性为None，导致调用失败。

### 解决方案
发现函数存储在`coroutine`属性，实现多层级函数提取。

**核心代码：**
```python
def register_langchain_tool(self, langchain_tool):
    func = None
    if hasattr(langchain_tool, 'coroutine') and langchain_tool.coroutine:
        func = langchain_tool.coroutine  # 关键发现
    elif hasattr(langchain_tool, 'func') and langchain_tool.func:
        func = langchain_tool.func
```

**收益：** 100%兼容LangChain工具，无需重写现有代码。

## 9. 知识图谱技术选型

### 问题描述
需要实现实体关系抽取和图谱查询，在轻量级和专业级方案间选择。

### 方案对比

#### 轻量级方案（PostgreSQL）
**优势：**
- 无需新服务，复用现有数据库
- 部署简单，维护成本低
- 小规模（<10000实体）性能足够
- 学习成本低，SQL即可

**劣势：**
- 复杂图查询性能差（3跳以上）
- 缺少图算法（PageRank、社区发现）
- 递归查询需要CTE，写法复杂

**适用场景：**
- 演示项目、学习项目
- 小型企业应用
- 实体数<10000
- 简单关系查询

#### 专业级方案（Neo4j）
**优势：**
- 原生图存储，查询性能优秀
- 内置丰富图算法
- Cypher语言简洁直观
- 支持大规模图谱（百万级）

**劣势：**
- 需要额外服务（内存+1-3GB）
- 学习成本高（Cypher语言）
- 部署复杂度增加
- 运维成本高

**适用场景：**
- 中大型企业应用
- 实体数>10000
- 需要复杂图算法
- 性能要求高

### 实现方案（轻量级）

**核心代码：**
```python
class KnowledgeGraphService:
    async def add_entity(self, name: str, type: str):
        # 存储到 kg_entities 表
        
    async def add_relation(self, subject: str, predicate: str, object: str):
        # 存储到 kg_relations 表
        
    async def query_path(self, start: str, end: str, max_depth: int = 3):
        # 使用递归CTE查询路径
        sql = """
            WITH RECURSIVE paths AS (
                SELECT subject_id, object_id, ARRAY[subject_id] as path
                FROM kg_relations WHERE subject_id = :start
                UNION ALL
                SELECT r.subject_id, r.object_id, p.path || r.subject_id
                FROM kg_relations r JOIN paths p ON r.subject_id = p.object_id
                WHERE p.depth < :max_depth
            )
            SELECT path FROM paths WHERE object_id = :end
        """
```

| 最短路径 | 1000ms | 100ms | 10x |
| 内存占用 | +50MB | +1-3GB | 20-60x |

**收益：** 在保持轻量级的同时，实现了基础知识图谱功能，适合演示和小规模应用。

## 12. RAG检索精准度优化

### 问题描述
传统单路向量检索存在局限：
- 查询理解不够深入，无法捕捉多角度意图
- 检索结果缺少多样性，容易陷入相似内容
- 上下文构建简单粗暴，直接拼接导致信息冗余
- 缺少查询意图识别，所有查询一视同仁

### 业界先进方案分析

参考HelloAgents等先进RAG系统，发现关键技术：

**1. HyDE (Hypothetical Document Embeddings)**
- 生成假设文档，理解用户真实意图
- 用假设文档的向量进行检索，提升召回率

**2. 多查询生成**
- 将查询改写为多个不同角度的问题
- 并行检索，扩大覆盖面

**3. MMR (Maximal Marginal Relevance)**
- 平衡相关性和多样性
- 避免返回过于相似的结果

**4. 查询意图识别**
- 识别总结、事实、对比、操作等不同意图
- 动态调整检索参数（top_k、阈值）

### 技术方案对比

#### 业界方案（HelloAgents）

**优势：**
- 技术先进：HyDE + MMR + 多路检索
- 召回率高：多角度查询覆盖全面
- 结果质量高：专门的重排序模块

**劣势：**
- 复杂度高：多个模块协调
- 性能开销大：多次LLM调用
- 资源消耗多：更多token和计算
- 调试困难：多环节可能出错

#### 我们的原始方案

**优势：**
- 实现简单：单路向量检索
- 性能优秀：响应快（1.2s）
- 成本可控：token消耗少
- 易于维护：代码清晰

**劣势：**
- 查询理解简单：无改写和扩展
- 检索单一：仅依赖向量相似度
- 缺少多样性：可能返回重复内容
- 意图识别基础：简单关键词判断

**设计原则：**

**核心实现：**

```python
class QueryOptimizer:
    """查询优化器"""
    
    async def rewrite_query(self, query: str, num_variants: int = 3):
        """查询改写 - 生成多个不同角度的查询"""
        prompt = f"""请将以下查询改写为{num_variants}个不同角度的问题
        
原始查询: {query}

要求:
1. 保持原意，但从不同角度表达
2. 可以是更具体的问题，也可以是相关的问题
3. 每个问题一行，不要编号

改写后的查询:"""
        
        response = await llm_service.get_answer(prompt, [], [])
        variants = [line.strip() for line in response.split('\n') if line.strip()]
        return variants
    
    def mmr_rerank(self, results, query_embedding, lambda_param=0.5):
        """MMR重排序 - 平衡相关性和多样性"""
        selected = []
        remaining = results.copy()
        
        # 选择第一个（最相关的）
        first = max(remaining, key=lambda x: x['score'])
        selected.append(first)
        remaining.remove(first)
        
        # 迭代选择剩余结果
        while remaining and len(selected) < top_k:
            best_score = -float('inf')
            best_item = None
            
            for item in remaining:
                # 相关性分数
                relevance = cosine_similarity(query_embedding, item['embedding'])
                
                # 多样性分数（与已选择结果的最大相似度）
                max_similarity = max(
                    cosine_similarity(item['embedding'], s['embedding'])
                    for s in selected
                )
                
                # MMR分数 = λ * 相关性 - (1-λ) * 最大相似度
                mmr_score = lambda_param * relevance - (1 - lambda_param) * max_similarity
                
                if mmr_score > best_score:
                    best_score = mmr_score
                    best_item = item
            
            if best_item:
                selected.append(best_item)
                remaining.remove(best_item)
        
        return selected
    
    async def detect_query_intent(self, query: str):
        """查询意图识别"""
        intent = {"type": "general", "suggested_top_k": 5}
        
        # 总结类查询
        if any(word in query for word in ["总结", "概括", "归纳"]):
            intent["type"] = "summary"
            intent["suggested_top_k"] = 15
            intent["suggested_threshold"] = 0.25
        
        # 事实类查询
        elif any(word in query for word in ["什么是", "定义", "解释"]):
            intent["type"] = "factual"
            intent["suggested_top_k"] = 3
            intent["suggested_threshold"] = 0.4
        
        return intent
```

```python
    def __init__(self):
        self.enable_query_rewrite = True   # 查询改写
        self.enable_hyde = False           # HyDE（可选）
        self.enable_mmr = True             # MMR重排序
    
    async def search(self, query: str, top_k: int = 5, use_optimization: bool = True):
        # 1. 查询意图检测
        intent = await query_optimizer.detect_query_intent(query)
        
        # 2. 查询改写（生成2-3个变体）
        queries = [query]
        if use_optimization and self.enable_query_rewrite:
            queries = await query_optimizer.rewrite_query(query, num_variants=2)
        
        # 3. 多查询检索
        all_results = []
        for q in queries:
            q_embedding = await embedding_service.get_embedding(q)
            results = await self._vector_search(q_embedding, top_k=top_k*2)
            all_results.extend(results)
        
        # 4. 去重和合并
        unique_results = self._deduplicate_results(all_results)
        
        # 5. MMR重排序
        if use_optimization and self.enable_mmr:
            reranked = query_optimizer.mmr_rerank(
                unique_results,
                main_query_embedding,
                lambda_param=0.6  # 60%相关性，40%多样性
            )

        return unique_results[:top_k]
```

**MMR算法核心思想：**
```
MMR分数 = λ * 相关性 - (1-λ) * 多样性

其中：
- λ=1: 完全按相关性排序（退化为传统检索）
- λ=0: 完全按多样性排序（可能丢失相关性）
- λ=0.6: 平衡点（60%相关性 + 40%多样性）
```

**实现细节：**
- 贪心算法：每次选择MMR分数最高的
- 时间复杂度：O(n²)，可接受（n通常<20）
- 空间复杂度：O(n)

```python
    """
    字体大小层级分析算法
    
    1. 统计所有字体大小的出现频率
    2. 识别正文字体（最频繁）
    3. 大于正文字体的按降序排列 → 标题层级
    4. 构建字体大小到标题级别的映射
    """
    font_counter = Counter(font_sizes)
    body_font_size = font_counter.most_common(1)[0][0]  # 正文字体
    
    heading_fonts = sorted([
        size for size in font_counter.keys() 
        if size > body_font_size
    ], reverse=True)
    
    # 字体大小 → 标题级别映射
    font_hierarchy = {}
    for i, font_size in enumerate(heading_fonts[:6]):
        font_hierarchy[font_size] = i + 1
    
    return font_hierarchy
```

   ```python
   file_type = Column(String(200), nullable=True)  # 200字符足够容纳所有MIME类型
   ```

## 13. MCP服务器开发与部署

### 问题描述
需要将计算密集型工具（税务计算、法律匹配、财务分析）部署到云端，供本地Agent调用。涉及服务开发、容器化部署、网络配置和前后端通信调试。

### 技术架构

**MCP (Model Context Protocol)** 是一种客户端-服务器架构的协议，支持两种传输方式：
- **SSE (Server-Sent Events)**：服务端推送，适用实时通知
- **HTTP/REST**：简单易用，适用请求-响应模式

### 方案对比

#### 方案A：标准MCP协议 + SSE
**优势：**
- 符合MCP官方规范
- 支持服务端推送
- 与MCP客户端SDK无缝对接

**劣势：**
- 实现复杂度高
- 需要完整的MCP SDK支持
- 调试困难

#### 方案B：自定义HTTP API
**优势：**
- 实现简单，易于调试
- 与现有HTTP客户端完全兼容
- 前后端分离清晰

**劣势：**
- 非标准协议
- 缺少实时推送能力
- 需要手动管理连接状态

### 最终选择：方案B（自定义HTTP API）

**理由：**
1. **需求匹配**：工具调用是请求-响应模式，不需要实时推送
2. **快速开发**：减少协议实现的复杂度
3. **易于调试**：标准HTTP协议，可直接用curl/浏览器测试
4. **降低耦合**：前后端独立演进，互不影响

### 核心实现

**服务端 (FastAPI)：**
```python
class MCPCallRequest(BaseModel):
    tool_name: str
    arguments: Dict[str, Any] = {}

@app.post("/mcp/call")
async def mcp_call(request: MCPCallRequest):
    tool = registry.get(request.tool_name)
    result = await tool.run(**request.arguments)
    return {"jsonrpc": "2.0", "result": result, "id": request.tool_name}
```

**客户端 (httpx)：**
```python
async def call_tool(self, tool_name: str, arguments: Dict[str, Any]) -> Dict[str, Any]:
    async with httpx.AsyncClient(timeout=self.timeout) as client:
        response = await client.post(
            f"{self.base_url}/mcp/call",
            headers=self.headers,
            json={"tool_name": tool_name, "arguments": arguments}  # 注意用json而非params
        )
        return response.json()
```

### 问题排查过程

#### 问题1：502 Bad Gateway
**现象：** 宿主机无法访问云端MCP服务
**排查步骤：**
1. 检查容器日志 → uvicorn正常运行
2. 检查nginx配置 → 语法正确
3. 阿里云安全组 → 发现8080端口未开放

**解决方案：** 在阿里云控制台添加入方向安全组规则，开放8080端口

#### 问题2：SSE连接卡住
**现象：** 连接成功但无法获取工具列表
**排查步骤：**
1. 客户端使用MCP SDK的SSE客户端
2. 服务器使用自定义SSE事件格式
3. 协议不匹配导致解析失败

**解决方案：** 改用HTTP API方式，避免协议歧义

#### 问题3：422 Unprocessable Entity
**现象：** 健康检查成功，但工具调用失败
**原因：** 客户端使用`params`传递参数，服务器期望`json body`

**解决方案：**
```python
# 错误
client.post(url, params={"tool_name": name, "arguments": args})

# 正确
client.post(url, json={"tool_name": name, "arguments": args})
```

### 面试价值

**Q: 为什么选择HTTP API而不是标准MCP协议？**
A:
1. **需求驱动**：工具调用是同步请求-响应模式，不需要SSE的实时推送能力
2. **简化实现**：减少协议解析的复杂度，专注业务逻辑
3. **易于调试**：标准HTTP协议，可直接用curl测试，降低排查成本
4. **保持扩展性**：如未来需要实时推送，可在现有基础上增加SSE端点

**Q: 如何快速定位云服务部署问题？**
A:
1. **日志分析**：首先查看容器日志，定位应用层问题
2. **分层排查**：应用层(uvicorn) → 反向代理(nginx) → 网络层(安全组/防火墙)
3. **本地验证**：在云服务器本地访问127.0.0.1，排除网络层问题
4. **工具辅助**：使用curl/netstat等工具逐步验证各层连通性

**Q: 容器内没有常用命令怎么办？**
A:
1. **精简镜像**：python:3.12-slim等精简镜像默认不包含ps/curl等工具
2. **临时方案**：安装所需工具 `apt-get install procps curl`
3. **替代方案**：使用docker自带的命令 `docker exec cat /proc/1/cmdline`
4. **镜像选择**：如需频繁调试，可使用包含常用工具的镜像如debian:stable

**Q: 如何设计前后端API的请求格式？**
A:
1. **POST请求用body**：复杂数据（JSON对象、嵌套参数）用JSON body
2. **GET请求用query**：简单筛选条件用query string
3. **RESTful规范**：资源操作用POST/GET/PUT/DELETE
4. **避免歧义**：明确区分params(路径参数/query参数)和json body
