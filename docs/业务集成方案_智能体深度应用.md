## 一、现状分析

### 1.1 现有系统能力盘点

经过对后端代码的全面审查，当前系统已具备以下核心能力：

| 组件模块 | 文件位置 | 核心功能 | 成熟度 |
|---------|---------|---------|--------|
| **多智能体协调器** | `multi_agent_system/coordinator.py` | 统一管理Finance、Legal、Tax、Policy等专家智能体，支持RAG检索和记忆系统 | ✅ 基础完备 |
| **智能体追踪服务** | `services/agent_tracer.py` | 记录智能体执行全链路，支持审计追溯 | ✅ 基础完备 |
| **人工审核队列** | `multi_agent_system/human_review.py` | 实现人机协作审核，支持6种触发条件 | ✅ 基础完备 |
| **财务数据工具** | `agent_framework/tools/financial_data_tools.py` | 查询用户财务数据、执行税务计算 | ✅ 基础完备 |
| **报告生成引擎** | `multi_agent_system/report_generator.py` | 从审计状态生成结构化报告 | ✅ 基础完备 |
| **政策检索服务** | `services/policy_retrieval_service.py` | 语义搜索、关键词搜索、企业政策匹配 | ✅ 基础完备 |
| **管理员通知服务** | `services/admin_notification_service.py` | 检测高风险AI操作，触发通知和人工审核 | ✅ 基础完备 |

### 1.2 专家智能体能力现状

| 智能体 | 领域覆盖 | 当前能力 | 存在问题 |
|-------|---------|---------|---------|
| **FinanceSpecialist** | 投资、贷款、预算、财务报表、成本控制、现金流、 Treasury | 实体提取、领域识别 | 仅限分析，无实际操作能力 |
| **TaxSpecialist** | 增值税、企业所得税、个人所得税、消费税等 | 税务类型判断、计算规则 | 缺乏与真实数据连接 |
| **LegalSpecialist** | 合同、知识产权、劳动合同、公司法、合规等 | 合同类型识别、条款分类 | 无法执行合同审核 |
| **PolicyAgent** | 国家、省、市、部门政策 | 政策收集、解析、影响分析 | 缺乏主动推送能力 |

### 1.3 核心问题诊断

**当前系统的最大问题**：三大专家智能体（Finance、TruckLegal、Tax）停留在「领域分类和实体识别」层面，无法解决具体业务问题。

```
现状：用户问"帮我分析这份合同的风险" 
     → LegalSpecialist识别出合同类型 → 返回"这是一份采购合同，涉及X类条款"
     → 业务价值≈0，用户仍需人工处理

期望：用户问"帮我分析这份合同的风险"
     → LegalSpecialist深度分析条款 → 识别风险点 → 给出修改建议 → 触发法务审核 → 生成报告
     → 业务价值=大幅减少法务工作量
```

## 二、业务痛点深度剖析

### 2.1 痛点一：税务合规负担重

**问题描述**：
- 财务人员手工计算税负，效率低、易出错
- 税收优惠政策种类繁多，人工难以全部掌握
- 政策更新频繁，跟踪不及时导致错过优惠或产生风险
- 税务申报需要反复核对，工作量大

**现状痛点程度**：⭐⭐⭐⭐⭐（非常痛）

**涉及岗位**：税务专员、财务经理、会计

**每年耗时估算**：中型企业约 200-400 人力小时

### 2.2 痛点二：财务异常发现滞后

**问题描述**：
- 依赖季度/年报分析，发现问题时已造成损失
- 财务指标异常靠人工比对，难以发现隐蔽问题
- 现金流紧张无法提前预警
- 历史数据分散，趋势分析困难

**现状痛点程度**：⭐⭐⭐⭐（很痛）

**涉及岗位**：财务总监、CFO、财务分析员

**潜在风险**：可能导致资金链断裂、重大亏损

### 2.3 痛点三：政策法规跟踪困难

**问题描述**：
- 政策数量庞大，人工筛选工作量大
- 政策适用性判断依赖经验，容易遗漏
- 新政策影响分析不够全面
- 缺乏主动推送机制

**现状痛点程度**：⭐⭐⭐⭐（很痛）

**涉及岗位**：法务、合规、财务、管理层

**潜在风险**：政策合规风险、错过优惠

### 2.4 痛点四：合同审核效率低

**问题描述**：
- 法务人员审核大量标准合同，耗时且重复
- 风险识别依赖个人经验，不一致
- 新合同起草缺乏参考
- 历史合同难以复用

**现状痛点程度**：⭐⭐⭐⭐⭐（非常痛）

**涉及岗位**：法务专员、法务经理

**每年耗时估算**：中型企业约 300-600 人力小时

```python
def match_policies_to_enterprise(enterprise: Enterprise, policies: List[Policy]) -> List[MatchedPolicy]:
    """将政策与企业匹配"""
    matches = []
    for policy in policies:
        score = 0
        
        # 行业匹配
        if policy.industry == enterprise.industry:
            score += 40
        
        # 地区匹配
        if policy.region in [enterprise.region, 'NATIONAL']:
            score += 30
        
        # 规模匹配
        if policy.scale_range.contains(enterprise.scale):
            score += 20
        
        # 类型匹配
        if policy.enterprise_type == enterprise.type:
            score += 10
        
        if score >= 60:  # 阈值
            matches.append(MatchedPolicy(policy=policy, score=score))
    
    return sorted(matches, key=lambda x: x.score, reverse=True)
```

## 十四、高级能力扩展：跨领域协同与深度集成

### 14.1 跨领域智能体协同 (Multi-Agent A2A Collaboration)

#### 14.1.1 引入必要性分析

**必要性评级：⭐⭐⭐⭐⭐（极高，一票否决项）**

当前四个业务场景（税务合规、财务监控、政策追踪、合同管理）均采用"单智能体单任务"模式。然而，企业真实业务高度交织，单一视角的分析往往遗漏关键风险。

**典型场景：重大合同综合评审**

以《重大设备采购及安装合同》为例，一份合同涉及：

| 维度 | 审查内容 | 单一智能体局限 |
|-----|---------|--------------|
| **法律** | 管辖权条款、违约金比例、知识产权归属、履约保障 | 仅能看到条款文字，无法评估财务影响 |
| **财务** | 首付款比例、现金流压力、付款周期与回款匹配 | 仅能看数字，无法判断法律风险等级 |
| **税务** | 发票类型（专票/普票）、税费承担方、跨境关税 | 仅能算税，无法评估合同整体风险 |

单一智能体只能输出单一维度的分析报告，业务人员需要人工整合三个报告才能做决策。A2A 协同的价值在于：**一次输入，三维并行分析，自动合成综合评审报告**。

#### 14.1.2 技术实现方案

**核心架构扩展**：

```python
# coordinator.py 新增 A2A 协同能力

class AgentCoordinator:
    async def process_complex_task(self, request: ComplexTaskRequest) -> ComprehensiveReport:
        """处理复杂跨领域任务"""
        # Step 1: 任务拆解
        subtasks = await self.decompose_task(request)
        
        # Step 2: 并行派发给多个专家智能体
        results = await self.dispatch_parallel(subtasks)
        
        # Step 3: 收集各智能体结果
        legal_result = results.get("legal")
        finance_result = results.get("finance")
        tax_result = results.get("tax")
        
        # Step 4: 综合分析与报告生成
        comprehensive_report = await self.synthesize_results(
            legal=legal_result,
            finance=finance_result,
            tax=tax_result,
            original_request=request
        )
        
        return comprehensive_report
    
    async def decompose_task(self, request: ComplexTaskRequest) -> List[SubTask]:
        """将复杂任务拆解为子任务"""
        # 分析输入内容，识别涉及的领域
        # 例如：合同文本 → 法律分析 + 财务分析 + 税务分析
        
        subtasks = []
        
        # 法律维度子任务
        if self._requires_legal_review(request):
            subtasks.append(SubTask(
                type="LEGAL",
                agent_type="LegalSpecialist",
                input=self._extract_legal_content(request),
                priority=HIGH
            ))
        
        # 财务维度子任务
        if self._requires_finance_review(request):
            subtasks.append(SubTask(
                type="FINANCE",
                agent_type="FinanceSpecialist",
                input=self._extract_finance_content(request),
                priority=HIGH
            ))
        
        # 税务维度子任务
        if self._requires_tax_review(request):
            subtasks.append(SubTask(
                type="TAX",
                agent_type="TaxSpecialist",
                input=self._extract_tax_content(request),
                priority=HIGH
            ))
        
        return subtasks
    
    async def dispatch_parallel(self, subtasks: List[SubTask]) -> Dict[str, SubTaskResult]:
        """并行派发任务给多个智能体"""
        # 使用 asyncio.gather 实现真正的并行执行
        async def execute_subtask(subtask: SubTask):
            agent = self._get_agent(subtask.agent_type)
            return subtask.type, await agent.process(subtask.input)
        
        results = await asyncio.gather(
            *[execute_subtask(st) for st in subtasks],
            return_exceptions=True
        )
        
        return {r[0]: r[1] for r in results if not isinstance(r, Exception)}
```

```python
            status=ProcessStatus.PENDING,

            "Pending": ProcessStatus.PENDING,
            "Running": ProcessStatus.RUNNING,
            "Successful": ProcessStatus.COMPLETED,
            "Failed": ProcessStatus.FAILED
```

### 14.3 基于图谱的语义记忆 (GraphRAG Semantic Memory)

#### 14.3.1 引入必要性分析

**必要性评级：⭐⭐⭐⭐（高）**

VectorDB 擅长"语义相似性检索"，但不擅长"关系推理"。当企业架构复杂时，这成为致命短板：

**典型风险场景：隐蔽关联交易识别**

```
集团财务公司向 A 公司支付"咨询服务费"500万

VectorDB 分析：
- 检索"咨询服务费"
- 返回：正常业务往来，无异常
- 结果：✅ 无风险

GraphRAG 分析：
- 图谱查询：A公司 → 股权穿透 → 实际控制人 = 董事长配偶
- 图谱查询：A公司与集团的股权层级 = 3层嵌套
- 图谱关联：过去12个月，集团向A公司累计支付2000万
- 结论：🔴 高度疑似关联交易，可能构成关联方资金占用
```

没有图谱，Agent 只能看到"点"（单笔交易），无法发现"线"（交易链路）和"网"（关系网络）。

```python
# graph_memory/enterprise_graph.py

class EnterpriseGraph:
    """企业关系知识图谱"""
    
    def __init__(self, neo4j_connection: Neo4jConnection):
        self.driver = neo4j_connection.driver
    
    async def build_company_node(
        self,
        company: CompanyInfo,
        ownership_chain: List[OwnershipLink]
    ) -> None:
        """构建公司节点及其股权链"""
        async with self.driver.session() as session:
            # 创建公司节点
            await session.run("""
                MERGE (c:Company {id: $company_id})
                SET c.name = $name,
                    c.industry = $industry,
                    c.registration_date = $registration_date,
                    c.business_scope = $business_scope
            """, **company.dict())
            
            # 创建股权关系边
            for link in ownership_chain:
                await session.run("""
                    MATCH (parent:Company {id: $parent_id})
                    MATCH (child:Company {id: $child_id})
                    MERGE (parent)-[r:OWNS {
                        share_percentage: $share_percentage,
                        established_date: $established_date
                    }]->(child)
                """, **link.dict())
    
    async def add_transaction_edge(
        self,
        transaction: Transaction
    ) -> None:
        """添加交易关系边"""
        async with self.driver.session() as session:
            await session.run("""
                MATCH (from:Company {id: $from_company_id})
                MATCH (to:Company {id: $to_company_id})
                MERGE (from)-[r:TRANSFERRED {
                    transaction_id: $transaction_id,
                    amount: $amount,
                    currency: $currency,
                    transaction_type: $transaction_type,
                    purpose: $purpose,
                    date: $date
                }]->(to)
            """, **transaction.dict())
    
    async def find_related_parties(
        self,
        company_id: str,
        depth: int = 3
    ) -> List[RelatedPartyInfo]:
        """查找关联公司（穿透股权）"""
        async with self.driver.session() as session:
            result = await session.run("""
                MATCH path = (c:Company {id: $company_id})-[:OWNS*1..%d]-(related:Company)
                WHERE c <> related
                RETURN path, 
                       REDUCE(total = 0, r IN relationships(path) | total + r.share_percentage) AS cumulative_share
                ORDER BY cumulative_share DESC
                LIMIT 20
            """ % depth, company_id=company_id)
            
            return [RelatedPartyInfo.from_path(row["path"], row["cumulative_share"]) 
                    for row in result]

class GraphEnhancedFinanceSpecialist:
    """图增强的财务智能体"""
    
    def __init__(self, enterprise_graph: EnterpriseGraph, ...):
        self.graph = enterprise_graph
        ...

        self,
        transaction: Transaction
    ) -> TransactionRiskReport:

        # Step 1: 基础财务分析
        base_analysis = await self._basic_financial_analysis(transaction)
        
        # Step 2: 图谱关联分析
        graph_analysis = await self._graph_relationship_analysis(transaction)
        
        # Step 3: 合并风险评估

            graph_analysis

        # 如果发现关联关系，提升风险等级

            combined_risk.flags.append(

            )
        
        return combined_risk
    
    async def _graph_relationship_analysis(
        self,
        transaction: Transaction

        """图谱关系分析"""
        
        # 查找交易双方的股权链
        from_parties = await self.graph.find_related_parties(
            transaction.from_company_id,
            depth=3
        )
        to_parties = await self.graph.find_related_parties(
            transaction.to_company_id,
            depth=3
        )
        
        # 检查是否存在交叉关联
        from_ids = {p.company_id for p in from_parties}
        to_ids = {p.company_id for p in to_parties}
        
        common_companies = from_ids & to_ids
        
        if common_companies:
            # 发现关联交易
            return GraphAnalysisResult(
                has_hidden_relationship=True,
                relationship_type="股权交叉关联",
                related_party_id=next(iter(common_companies)),
                evidence=f"双方均与公司{next(iter(common_companies))}存在股权关系"
            )
        
        # 检查是否与集团核心成员有关联
        if transaction.to_company_id in from_ids:
            return GraphAnalysisResult(
                has_hidden_relationship=True,
                relationship_type="交易对手为关联方",
                related_party_id=transaction.to_company_id,
                evidence="交易对手在股权链中"
            )
        
        return GraphAnalysisResult(has_hidden_relationship=False)
```

```python
        # Step 2: 图谱检索获取关系信息
        if context_type == ContextType.FINANCIAL_TRANSACTION:
            graph_results = await self._retrieve_transaction_context(company_id)
        elif context_type == ContextType.CONTRACT_ANALYSIS:
            graph_results = await self._retrieve_contract_context(company_id)
        else:
            graph_results = []
        
        # Step 3: 合并去重
        combined_context = self._merge_and_rank(
            vector_results=vector_results,
            graph_results=graph_results
        )
        
        return combined_context
    
    async def _retrieve_transaction_context(
        self,
        company_id: str
    ) -> List[GraphResult]:
        """检索交易上下文"""
        
        # 查找最近12个月的关联交易
        recent_transactions = await self.graph.find_transactions(
            company_id=company_id,
            date_range=DateRange(
                start=datetime.now() - timedelta(days=365),
                end=datetime.now()
            ),
            limit=20
        )
        
        # 查找关联公司
        related_parties = await self.graph.find_related_parties(
            company_id=company_id,
            depth=3
        )
        
        return [
            GraphResult(
                type="related_transaction",
                content=tx.summary,
                relevance_score=0.9
            )
            for tx in recent_transactions
        ] + [
            GraphResult(
                type="related_party",
                content=party.relationship_description,
                relevance_score=0.85
            )
            for party in related_parties[:5]
        ]
```

### 14.4 数据脱敏与安全边界 (Data Masking Gateway)

#### 14.4.1 引入必要性分析

**必要性评级：⭐⭐⭐⭐⭐（极高，一票否决项）**

这是企业在采购 AI 系统时首要关注的问题：

**合规要求**：

| 法规/标准 | 相关要求 | 违反后果 |
|----------|---------|---------|
| 《数据安全法》 | 重要数据不得出境 | 最高1000万罚款 |
| 《个人信息保护法》 | 处理个人信息需授权 | 最高5000万罚款 |
| 金融行业监管 | 客户信息本地化存储 | 业务许可暂停 |
| 国资监管要求 | 核心经营数据不得上传境外 | 问责处分 |

**商业风险**：

```
场景：某国企财务总监使用AI系统分析年报数据

数据流向（无脱敏）：
财务数据 → 传给云端LLM（如Claude/智谱） → 返回分析结果
         ↓
        包含真实营收、客户信息、供应商名单的商业机密

风险：
- LLM可能将数据用于模型训练
- API服务商数据泄露
- 竞争对手通过某种渠道获取
```

**国企/金融机构的采购要求**：

> "乙方不得将甲方提供的任何数据、文件、资料用于本合同约定以外的任何目的，不得将上述信息存储于境外服务器，不得将上述信息提供给任何第三方"

这是招标文件的标配条款，无脱敏能力 = 无投标资格。

```python
# security/data_masking_gateway.py

class DataMaskingGateway:
    """数据脱敏网关"""
    
    def __init__(
        self,
        mask_config: MaskingConfig,
        mapping_store: MappingStore
    ):
        self.config = mask_config
        self.mapping_store = mapping_store
        self.entity_recognizer = self._init_entity_recognizer()
    
    def _init_entity_recognizer(self) -> LocalNERModel:
        """初始化本地轻量级实体识别模型"""
        # 使用 LLaMA.cpp 本地推理 或 轻量级规则引擎
        return LocalNERModel(
            model_path=self.config.ner_model_path,
            device="cpu",  # 本地CPU推理
            quantization="int8"
        )
    
    async def mask_data(self, raw_data: Union[str, dict]) -> MaskedData:
        """对原始数据进行脱敏"""
        
        # 生成唯一会话ID
        session_id = str(uuid.uuid4())
        
        # 提取文本内容
        if isinstance(raw_data, dict):
            text_content = self._flatten_to_text(raw_data)
        else:
            text_content = raw_data
        
        # Step 1: 实体识别
        entities = await self.entity_recognizer.recognize(text_content)
        
        # Step 2: 实体替换与映射
        masked_text, entity_mapping = self._substitute_entities(
            text_content,
            entities,
            session_id
        )
        
        # Step 3: 存储映射关系（本地，永不上传）
        await self.mapping_store.save(
            session_id=session_id,
            mapping=entity_mapping
        )
        
        # Step 4: 构建脱敏数据结构
        masked_data = MaskedData(
            session_id=session_id,
            masked_text=masked_text,
            original_structure=raw_data if isinstance(raw_data, dict) else None,
            entity_count=len(entity_mapping),
            masked_at=datetime.now()
        )
        
        return masked_data
    
    def _substitute_entities(
        self,
        text: str,
        entities: List[Entity],
        session_id: str
    ) -> Tuple[str, Dict[str, str]]:
        """替换实体为占位符"""
        
        mapping = {}
        masked_text = text
        
        for entity in entities:
            # 生成占位符
            placeholder = self._generate_placeholder(entity.type)
            
            # 建立映射关系
            mapping[placeholder] = entity.original_value
            
            # 替换文本中的实体
            masked_text = masked_text.replace(
                entity.original_value,
                placeholder
            )
        
        return masked_text, mapping
    
    def _generate_placeholder(self, entity_type: EntityType) -> str:
        """根据实体类型生成占位符"""
        placeholder_map = {
            EntityType.COMPANY: "公司{}",
            EntityType.PERSON: "人员{}",
            EntityType.AMOUNT: "金额{}",
            EntityType.BANK_ACCOUNT: "账户{}",
            EntityType.ID_CARD: "证件{}",
            EntityType.PHONE: "电话{}",
            EntityType.ADDRESS: "地址{}"
        }
        
        counter = self._get_counter(entity_type)
        return placeholder_map[entity_type].format(counter)
    
    async def unmask_result(
        self,
        session_id: str,
        masked_result: str
    ) -> str:
        """将脱敏结果逆向映射回原始数据"""
        
        # 获取映射关系
        mapping = await self.mapping_store.get(session_id)
        
        if not mapping:
            raise ValueError(f"Session {session_id} not found or expired")
        
        # 逆向替换
        unmasked_result = masked_result
        for placeholder, original_value in mapping.items():
            unmasked_result = unmasked_result.replace(placeholder, original_value)
        
        return unmasked_result

class LLMCallWithMasking:
    """带脱敏的LLM调用封装"""
    
    def __init__(
        self,
        llm_client: LLMClient,
        masking_gateway: DataMaskingGateway,
        audit_logger: AuditLogger
    ):
        self.llm = llm_client
        self.masker = masking_gateway
        self.audit = audit_logger
    
    async def chat(
        self,
        user_message: str,
        system_prompt: str,
        context: Optional[Dict] = None
    ) -> LLMResponse:
        """脱敏后调用LLM"""
        
        # Step 1: 脱敏用户消息
        masked_message = await self.masker.mask_data(user_message)
        
        # Step 2: 脱敏上下文
        masked_context = None
        if context:
            masked_context = await self.masker.mask_data(context)
        
        # Step 3: 记录审计日志（仅记录脱敏后数据）
        await self.audit.log_llm_call(
            session_id=masked_message.session_id,
            masked_request=masked_message.masked_text,
            context_entity_count=masked_context.entity_count if masked_context else 0
        )
        
        # Step 4: 调用LLM（仅传输脱敏数据）
        masked_response = await self.llm.chat(
            user_message=masked_message.masked_text,
            system_prompt=system_prompt,
            context=masked_context.masked_text if masked_context else None
        )
        
        # Step 5: 逆向映射结果
        final_response = await self.masker.unmask_result(
            session_id=masked_message.session_id,
            masked_result=masked_response.content
        )
        
        return LLMResponse(content=final_response)
```

```python
class MaskingConfig(BaseModel):

    # 是否启用脱敏（可配置关闭用于测试）
```

```python
        )
        
        return AgentResponse(content=final_response)
```

| **图谱风险** | 知识图谱数据滞后 | 建立增量更新机制，与工商数据实时同步 | P2 |
| **A2A风险** | 多智能体协同死锁或循环依赖 | 任务超时机制，防循环检测 | P2 |

## 十八、长文本处理与分块策略 (Long-Context & Chunking Strategy)

### 18.1 业务背景与痛点

| 痛点类型 | 具体表现 |
|---------|---------|
| **上下文窗口限制** | 100页合同 → Token数远超LLM限制 |
| **语义完整性破坏** | 简单截断分块 → 切断跨段落引用关系 |
| **信息定位偏差** | 传统关键词搜索 → 无法理解复杂语义 |
| **中间信息丢失** | "Lost in the Middle"问题 |

### 18.2 技术方案

```
┌─────────────────────────────────────────────────────────────┐
│                    Document Pipeline                         │
├─────────────────────────────────────────────────────────────┤
│  文档加载 → 语义分块 → 块索引 → Agent派发 → 报告生成           │
└─────────────────────────────────────────────────────────────┘
```

**核心策略：**
- **语义分块**：法律条款不可切断，保留条款间引用关系
- **Map-Reduce**：并行分析各分块，汇总综合报告
- **渐进式摘要**：块级→章节级→文档级多层摘要

### 18.3 典型场景

```
❌ 传统方式：
用户上传200页收购合同 → 系统报错"超出处理长度限制"

✅ 引入后：
系统自动识别合同结构 → 分块解析 → Map-Reduce并行分析 → 汇总风险报告
```

### 18.4 新增组件

| 组件 | 文件位置 | 功能 |
|-----|---------|------|
| SemanticChunker | `document_processing/semantic_chunker.py` | 语义分块器 |
| MapReduceOrchestrator | `document_processing/map_reduce_orchestrator.py` | Map-Reduce编排器 |
| ProgressiveSummary | `document_processing/progressive_summary.py` | 渐进式摘要生成器 |
| ChunkMetadataManager | `document_processing/chunk_metadata.py` | 分块元数据管理 |

## 十九、事件驱动架构 (Event-Driven Architecture, EDA)

### 19.1 业务背景与痛点

| 痛点类型 | 具体表现 |
|---------|---------|
| **被动响应限制** | 仅支持"用户查询-系统回答"，无法主动预警 |
| **轮询效率低下** | 定期检查ERP新数据 → 延迟高、资源浪费 |
| **松耦合缺失** | Agent间直接调用 → 一个故障影响全局 |
| **流程自动化难** | 跨系统操作需人工介入 |

### 19.2 技术方案

```
┌─────────────────────────────────────────────────────────────────┐
│                        Event-Driven Architecture                 │
├─────────────────────────────────────────────────────────────────┤
│  ERP事件监听 → Event Bus → Agent订阅 → 智能响应 → 编排执行        │
└─────────────────────────────────────────────────────────────────┘
```

**核心事件类型：**
| 事件类型 | 触发条件 | 预期响应 |
|---------|---------|---------|
| `erp.new_transaction` | ERP新交易数据 | 税务影响分析 |
| `erp.large_payment` | 大额付款(>阈值) | 财务风险审查 |
| `policy.new_released` | 新政策发布 | 影响分析+推送 |
| `user.upload_document` | 用户上传文档 | 自动分类+分析 |

### 19.3 典型场景

```
❌ 当前状态（被动查询）：
用户: "今天有什么新政策需要关注？" → 系统返回静态列表

✅ 引入后（主动智能）：
系统订阅政策发布源 → 检测到新政策 → 自动分析影响 → 推送相关用户
```

### 19.4 新增组件

| 组件 | 文件位置 | 功能 |
|-----|---------|------|
| EventBus | `events/event_bus.py` | 事件总线 |
| ERPEventListener | `events/erp_listener.py` | ERP事件监听器 |
| PolicyMonitor | `events/policy_monitor.py` | 政策发布监控 |
| AgentEventSubscriber | `events/agent_subscriber.py` | Agent事件订阅器 |

## 二十、数据飞轮与持续评估机制 (LLMOps & Feedback Loop)

### 20.1 业务背景与痛点

| 痛点类型 | 具体表现 |
|---------|---------|
| **模型静态不变** | 模型上线后无法学习用户反馈，知识陈旧 |
| **误判累积效应** | False Positive累积 → 用户逐渐忽略警告 |
| **性能黑盒化** | 无法量化Agent表现，无法针对性优化 |
| **微调数据匮乏** | 缺乏高质量领域微调数据 |

### 20.2 技术方案

```
┌─────────────────────────────────────────────────────────────────┐
│                      LLMOps & Feedback Loop                      │
├─────────────────────────────────────────────────────────────────┤
│  反馈收集 → 质量度量 → SFT数据管道 → 持续评估 → 模型迭代           │
└─────────────────────────────────────────────────────────────────┘
```

**反馈类型：**
| 反馈类型 | 采集方式 | 应用场景 |
|---------|---------|---------|
| 显式评分 | 用户主动评分 | 直接用于训练 |
| 显式纠正 | 用户纠正回答 | 高质量训练样本 |
| 隐式接受 | 保留AI建议 | 正样本 |
| 隐式拒绝 | 删除AI建议 | False Positive |
| 用户补充 | 添加AI未提及内容 | False Negative |

### 20.3 典型场景

```
❌ 当前状态（静态模型）：
系统标记"高风险" → 用户忽略 → 系统不知道对错 → 持续犯同类错误

✅ 引入后（持续学习）：
用户反馈(显式/隐式) → 记录为训练数据 → 周期性微调 → 准确率提升
```

### 20.4 新增组件

| 组件 | 文件位置 | 功能 |
|-----|---------|------|
| FeedbackCollector | `llmops/feedback_collector.py` | 反馈收集器 |

## 二十一、高可用性与优雅降级策略 (High Availability & Degradation)

### 21.1 业务背景与痛点

| 痛点类型 | 具体表现 |
|---------|---------|
| **单点依赖** | 依赖单一LLM API → API故障=系统瘫痪 |
| **无降级策略** | LLM不可用时直接报错 → 业务中断 |
| **资源浪费** | 失败不熔断 → 资源浪费、延迟飙升 |
| **SLA无保障** | 企业要求99.9%可用性 → 当前无法满足 |

### 21.2 技术方案

```
┌─────────────────────────────────────────────────────────────────┐
│                    High Availability Architecture                │
├─────────────────────────────────────────────────────────────────┤
│  请求路由 → 模型选择 → 熔断保护 → 降级执行 → 健康监控              │
└─────────────────────────────────────────────────────────────────┘
```

**降级级别：**
| 级别 | 状态 | 可用组件 | 预计准确率 |
|-----|------|---------|-----------|
| Level 1 | 正常 | LLM + KB + ERP | 100% |
| Level 2 | 部分 | LLM + KB（ERP手动） | 90% |
| Level 3 | 优雅 | 规则引擎 + KB | 70% |
| Level 4 | 完全 | 缓存 + 基础搜索 | 40% |

### 21.3 熔断器配置

| 参数 | 默认值 | 说明 |
|-----|-------|------|
| failure_threshold | 5 | 连续失败次数阈值 |
| recovery_timeout | 60s | 熔断恢复等待时间 |
| half_open_requests | 1 | 半开状态允许的测试请求数 |

### 21.4 典型场景

```
❌ 当前状态（脆弱架构）：
用户查询 → LLM超时 → 系统报错 → 业务中断

✅ 引入后（韧性架构）：
用户查询 → LLM超时 → 自动切换备选模型 → 返回结果（无感知）
```
